# Docker Core Concepts Cheat Sheet

## 1. Docker Image vs. Docker Container
* **Docker Image (The Blueprint):** A read-only, static template containing your application code, runtime, libraries, and OS dependencies. You can create many containers from a single image.
* **Docker Container (The Running Instance):** A live, runnable instance of an image. When you start an image, Docker adds a thin **read-write layer** on top of the image's read-only layers so the app can run and create temporary files.

---

## 2. What is a Layer?
A Docker image is built from a stack of **read-only filesystem layers**, where each instruction in a `Dockerfile` (`FROM`, `RUN`, `COPY`) creates a new layer representing only the file changes made in that step.
* **Why layers matter:** Docker caches and shares identical layers across different images, making builds faster and saving disk space.
* **Copy-on-Write (CoW):** When a running container modifies a file from the underlying image, Docker copies that file up into the container's writable layer before editing it—leaving the original image untouched.

---

## 3. Where Container Data Lives & When It Is Lost
* **Default Location (Ephemeral Writable Layer):** Any files created inside a container without external storage live in its top writable layer (managed by Docker's storage driver on the host, typically under `/var/lib/docker/`).
* **When It Is Lost:**
  * Stopping or restarting a container (`docker stop` / `docker restart`) **keeps** the data.
  * Removing the container (`docker rm`) **permanently destroys** all data inside that writable layer.

---

## 4. Volume vs. Bind Mount
To persist data beyond a container's lifecycle, you attach external storage:

| Feature | Docker Volume (`-v name:/path`) | Bind Mount (`-v /host/path:/path`) |
| :--- | :--- | :--- |
| **Who manages it?** | Docker manages the storage location automatically (`/var/lib/docker/volumes/`). | You specify an exact directory path on your host machine. |
| **Portability** | High (works identically across Linux, macOS, and Windows). | Low (depends on the host's folder structure). |
| **Performance** | Very fast, especially on macOS/Windows (Docker Desktop). | Slower on macOS/Windows due to filesystem translation. |
| **Best For** | Production databases (e.g., PostgreSQL data), persistent app state. | Local development (live-reloading source code or config files). |

---

## 5. What `-p 5433:5431` Means in Your PostgreSQL Command

```bash
docker run -d --name pg-lab -e POSTGRES_PASSWORD=lab -p 5433:5431 -v pg-lab-data:/var/lib/postgresql/data postgres:16
```

* **Syntax:** `-p <HOST_PORT>:<CONTAINER_PORT>`
* **`5433` (Host Port):** The port opened on your actual computer/server. External clients connect to `localhost:5433`.
* **`5431` (Container Port):** The port inside the container where Docker forwards that traffic.

> **Important Catch in Your Command:** By default, PostgreSQL inside the official `postgres:16` image listens on port **`5432`**, not `5431`. Unless you explicitly configure Postgres to listen on `5431` (e.g., via `-c port=5431`), connecting to `localhost:5433` will fail with a connection refused/reset error. To connect to default Postgres on host port `5433`, use **`-p 5433:5432`**.

---

## 6. Why `:latest` Is a Bad Production Tag
The `:latest` tag does **not** automatically mean "most stable"—it is simply the default mutable pointer pushed without a specific version tag.
* **Unpredictable Breaking Changes:** Pulling `:latest` today might download PostgreSQL `16.4`, while pulling it next month on a new server could download `17.0`, potentially breaking database compatibility or crashing your app.
* **No Reproducibility / Rollbacks:** If a deployment breaks, rolling back to `:latest` is meaningless because the tag points to the broken version.
* **Best Practice:** Always pin an explicit, immutable version tag in production (e.g., `postgres:16.4-alpine` or even an exact SHA256 digest).
